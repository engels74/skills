# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Repository Is

A content-only collection of Agent Skills, published for the [Agent Skills](https://agentskills.io) ecosystem and installed with the [`skills`](https://github.com/vercel-labs/skills) CLI. Every tracked file is Markdown, YAML, or the license. There is **no** package manifest, lockfile, build step, test suite, linter, formatter, type-checker, or CI workflow — `renovate.json` is the only automation config, and it manages nothing in-tree today.

The practical consequence: changes here are prose and frontmatter changes. Validation is manual and structural, not command-driven. Do not add build tooling or CI unless explicitly asked.

## Layout Contract

```
<vendor>/<skill-name>/SKILL.md          # required entry point
<vendor>/<skill-name>/references/*.md   # optional deep-dive docs
<vendor>/<skill-name>/agents/*.yaml     # optional per-client interface metadata
```

Three rules that the CLI and the README both depend on:

1. **The skill directory name must equal the frontmatter `name`.** This was the explicit reason for the `b859057` restructure ("moved into a directory whose name matches the frontmatter `name`").
2. **The parent directory is the vendor namespace** and must match `metadata.vendor` when that field is present (`astro/starlight-docs` → `vendor: astro`).
3. **`<vendor>/<skill-name>` is a public install path.** `README.md` documents single-skill installs as `npx skills add https://github.com/engels74/skills/tree/main/augmentcode/codebase-retrieval`. Renaming or moving a skill directory breaks that URL for existing users; treat it as a breaking change, not a refactor.

## Adding or Changing a Skill

1. Create `<vendor>/<skill-name>/SKILL.md` with YAML frontmatter (see below).
2. Put anything long-form in `references/*.md` and link it from `SKILL.md` with a path relative to the skill directory (`references/foo.md`). Reference files carry **no** frontmatter — they start directly with an `# H1`.
3. Add or update the row in the `## Skills` table in `README.md`. Both skill-adding commits (`d2bdcfc`, `399c4e5`) touch `README.md` in the same commit; that table is the repository's only index, so a skill added without it is effectively undiscoverable.
4. Commit with Conventional Commits, scoped to the vendor directory where one applies: `feat(pelican-eggs): add panel egg round-trip skill`, `chore(renovate): standardize fleet renovate policy`.

## SKILL.md Frontmatter

| Field | Status | Notes |
|---|---|---|
| `name` | required | Must equal the containing directory name. |
| `description` | required | Single physical line. See the gotcha below. |
| `compatibility` | when applicable | Free-text prerequisite; used by `codebase-retrieval` to state that the Augment MCP tool must be configured. |
| `license` | see conflict | Exactly `AGPL-3.0`. |
| `metadata.author` / `.version` / `.vendor` | see conflict | `engels74`, a quoted semver string, and the vendor directory name. |

Unresolved conflict: `astro/starlight-docs` and `augmentcode/codebase-retrieval` both carry `license` and the `metadata` block; the newest skill, `pelican-eggs/panel-egg-roundtrip`, carries only `name` and `description`. The repository does not state which is canonical. Prefer including `license` and `metadata` for new skills — that matches the deliberate normalization in `157b7f0` — but do not add them to `panel-egg-roundtrip` as a drive-by change.

## Critical Gotchas

- **`description:` must stay on one physical line.** All three skills use a single unwrapped line of roughly 440–1000 characters containing full sentences, quoted user phrasings, and backticked identifiers. Wrapping it, or reformatting it into a YAML block scalar, changes how clients parse and match the skill. Edit the line in place; do not "tidy" the frontmatter.
- **Write descriptions as trigger lists, not summaries.** The established pattern is: one sentence of what the skill does, then explicit "Use this skill whenever…" clauses naming concrete user phrasings, file paths, and package names, then a negative clause saying when *not* to use it (`starlight-docs`: "When the task is generic Astro work with no documentation theme involved, prefer general Astro knowledge instead"). A short generic description will not route correctly.
- **The license identifier is `AGPL-3.0`, never `AGPL-3.0-or-later`.** Commit `157b7f0` removed the `-or-later` suffix specifically because `LICENSE` is AGPL v3 with no "or later" clause. Keep frontmatter, `README.md`, and `LICENSE` in agreement.
- **`SKILL.md` is a router, not an encyclopedia.** `astro/starlight-docs/SKILL.md` is 102 lines and delegates ~3,000 lines to ten self-contained references, each mapped to a task ("Sidebar shape, autogenerated groups, badges, collapsing → `references/navigation-and-search.md`"). When content grows, add a reference and a routing line rather than expanding `SKILL.md`.
- **`agents/openai.yaml` is per-skill and optional.** Only `panel-egg-roundtrip` has one; it declares `interface.display_name`, `interface.short_description`, and `interface.default_prompt`. Do not add it to other skills speculatively, and keep `default_prompt` consistent with the skill's `name` (`$panel-egg-roundtrip`).

## Manual Validation Before Committing

There is no automated check, so verify by hand:

```bash
git ls-files '*/*/SKILL.md'    # each path's directory name must match its frontmatter `name`
```

Then confirm: every `references/…` link in a `SKILL.md` resolves relative to that skill's directory; the `README.md` table row exists and its link target is real; `license`/`metadata.vendor` agree with the directory path.
